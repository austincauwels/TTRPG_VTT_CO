# Quirks and suspected bugs found while pinning behavior (2026-10-04)

The characterization tests in backend/tests pin these AS THEY ARE, so the refactor
does not change them by accident. Each fix later gets its own commit and flips its test.

- On a fresh PostgreSQL database, users_id_seq and circles_id_seq start at (1, not called) because init_db inserts user 1 and circle 1 with explicit ids. The first register and the first auto-created campaign circle both return 500. The failed insert consumes the value, so the second attempt works. Fixed 2026-10-09 (playtest, seed-id-sequence-collision): init_db moves both sequences past the seeded rows (advance_seeded_sequences), so both work the first time. Tests: test_fresh_postgres_sequences_follow_the_seeded_ids, test_advancing_the_sequences_never_moves_them_back.
- Seeded admin/admin can log in on every new database.
- Register always returns campaignCode 'fairelands-01' (hard-coded). Usernames are case-sensitive for register and login, but invite-rejoin matches them case-insensitively.
- Forge: a missing user_id, user_id 0, or an unknown user_id makes the character belong to user 1. The client sets every stat with no bounds. The character is always placed on circle 1.
- GET /api/investigators always reports is_dead False, pen_font 'Caveat' and ink_color '' (those fields are never filled in). GET /api/investigators/{id} returns 500 for a character whose circle_id is NULL.
- create_campaign: a duplicate code returns an unhandled 500, an unknown gm_user_id returns 500 (FK), all-digit codes are accepted, and the code is validated before the name.
- join has no status check, so it moves an active character out of its campaign and into pending in another one (the character keeps its old ink).
- rejoin needs no invite and no GM approval. Because the session does not autoflush, a dead predecessor that is being retired in the same request still counts when the ink color is picked (the new character gets INK_COLORS[1]).
- GET /campaign/{id}/circle-creation-state is a GET that writes, and for an unknown campaign it returns 500 (FK violation on PostgreSQL).
- REST /circle/vote with an unknown vote_type commits the vote, then returns 500 (KeyError). REST relationship counter sets status 'countered' and keeps the original terms, while the WebSocket counter rewrites the terms and sets status back to 'proposed'. REST propose does not set last_actor_id.
- Members stay on circle 1, so a campaign circle's max_capacity and refill_resources count 0 members (finalize still uses 1 + active members).
- Notebook: an unknown character_id or campaign_id returns 500 (FK). role=GM and character_id in the query are trusted. A soft-deleted entry can still be edited and deleted again, and it still counts for page numbers. Upload stores the client's content type in the data URI and its response has no author_type key. A self entry with no character, or an unknown visibility value, is never shown to anyone.
- campaign_retired reaches only the GM, and released pending characters never receive roster_finalized, because statuses change before the broadcast.
- Valid JSON that is not an object (a list, a string, or a list payload) ends the socket without a close frame.
- update_drive stores any value (99, -5). The character dict clamps negatives to 0 on output. An unknown pool still sends character_update. Fixed 2026-10-07: only nerve, cunning and intuition, as a whole number from 0 to the drive's maximum; anything else gets action_rejected 422 and nothing is stored.
- update_gear with a non-string item commits the gear, then the log join raises and ends the socket.
- apply_advancement has no gate. new_ability appends the text to specialty_ability with '; ', which breaks exact-name ability checks.
- spend_resource reads the circle object loaded at connect time. If the GM enables spending after the player connected, the spend is silently ignored until the player's session commits something. The GM socket likewise counts a cached member list in refill_resources: after a rejoin it sets stitch to 1 while the circle_update it sends already reports max_capacity 2.
- A zero-dice roll with two sixes counts as critical even though the lower die is the result. resolve_gilded trusts the client's value, can be replayed at any time, and can never give a critical. A non-numeric chosen_value ends the socket.
- A negative drive_spent raises the drive above its max, commits that, and then the empty pool raises roll_error. The roll action is not validated (for example action='nerve_max' uses nerve_max as the rating). The roll's ability-use counter never counts anything.
- burn_resistance with a pending gilded choice logs 'burned resistance on X - ? . .' (blank outcome label).
- take_mark: when a soak ability is available the mark is not applied (it is lost if the offer is declined). Back Against the Wall is always offered as a soak and has no resolve branch, so such a character never takes a brain mark. An unknown mark_type sends character_update and stores nothing.
- The Endurance branch calls secrets.randbelow but main.py never imports secrets. The NameError ends the socket and the mark is not applied (bug D1).
- Premonitions intercept spends the seer's resistance but does not remove the target's mark. Behind Me can target a character in any campaign. The resolve soak branches do not check remaining resistance pips.
- apply_scar shift names can be any numeric column (nerve_max and body_marks were shifted in the test).
- SceneManager's gm_update_circle with circle_id 1 edits the shared circle 1 and pushes circle 1's data to the campaign. The circle name is not settable through gm_update_circle (bug D2).
- GM powers rest on a client-claimed role: a player socket that sends role GM can toggle reports. resolve_circle falls back to an unscoped lookup, so one GM can toggle another campaign's circle.
- gm_update_tension's character_update goes only to the GM key, not to the player.
- submit_assignment_report has no ownership or reports_open check. Unknown ids are stored and reported as 'Unknown', and every player receives every report.
- update_circle: a non-GM may lower stitch, refresh and train and may set every other field. A string value for a resource ends the socket. The milestone log fires at illumination 3, 6 and 9 (not 12, and not when the value goes down).
- circle_creation_vote with an unknown vote_type commits the vote, then the KeyError ends the socket. circle_backstory_update can overwrite the reserved 'reports' key. circle_relationship_respond on a GM code socket raises (int(game_id)) and ends the socket.
- Chat: the whisper target is an ILIKE pattern (% and _ act as wildcards, case-insensitive). A pending sender does not get their own message echoed. sender_name is client-claimed. @Environment is not restricted to the GM.
- WS add_notebook_entry writes into the payload's campaign_id, but broadcasts to the socket's own campaign. Its activity_log payload has no log_type.
- A campaign whose all-digit code equals a character id makes that character's socket resolve to the campaign's circle.
- Likely live bug: submit_assignment_report loses every report once backstory_answers is not empty. It changes the loaded dict in place and assigns the same object back, so SQLAlchemy writes nothing. The report is broadcast but is gone after a reload. Reports from sockets that loaded an empty dict at connect each write a new dict holding only their own report, so the last report replaces the earlier ones. Any stored chapter house or selected question means even the first report is lost.
- New: WS circle_relationship_respond from a socket whose session still holds an older copy of the row can be silently lost. A counter after the other player accepted sets the values the stale copy already has, so no UPDATE runs and the relationship stays accepted. A second, identical counter then works. The same stale-session cause affects other handlers.
- The comment at main.py 1488 says the context is re-resolved per message, but camp_id, camp_code and the circle are fixed at connect. Even chat's per-message campaign lookup sees a REST join only after something on that socket commits, because the identity map keeps the character loaded at connect.
- A character_id of 0 turns a player's roll into a Lightkeeper roll. A character_id of 1.5 matches no character, so a campaign member's chat goes only to its own channel with no ink. A bad character_id ('abc', object, list, true) drops the whole frame, even for actions that need no character.
- intercept_mark's soak offer to the interceptor has no 'options' key and does not apply the mark, after the nerve spend and the target's mark removal are already committed. Its soak map has no Back Against the Wall, unlike take_mark.
- On the 'gm' fallback channel, gm_reset_character can reset any unaffiliated character (campaign_id IS NULL). gm_end_assignment resets every active character with a NULL campaign, not the members of the circle it was given, and clears the scene of any circle id (no scoping).
- finalize_roster ties go to the first vote stored, because the vote query has no ORDER BY.
- A whisper from a socket with no campaign matches names with ILIKE across every campaign.
- get_char_dict sends a string ability_uses through unparsed, while gear and scars are parsed. dict() on a string ability_uses closes the socket in take_mark and resolve_ability_mark. The dict() call in roll is unreachable.
- On a database that grew through init_db, the added columns are TEXT and INTEGER (backstory_answers and ability_uses are TEXT DEFAULT '{}', and the booleans are INTEGER DEFAULT 0). On such a database the seed rows (admin, circle 1) are never written, because the seed query runs before the ALTERs and fails on the missing columns.
- A roll mod listed twice in ability_mods is applied twice. An overspent drive floors at 0 but the whole spend still goes into the pool.
- Not testable without changing app code: the elif order between extra_dice_fn/extra_dice and extra_gild/extra_gild_condition.

## Changed by the login token stage (2026-10-04)

The list above is kept as it was found. These entries no longer hold, or hold only in part, because access is now checked (docs/refactor/AUTH.md has the rules); their tests were rewritten to pin the new behavior. Everything else above is unchanged and still pinned.

- Seeded admin/admin (A5): init_db now gives admin a random password nobody is told. On every startup it also replaces the password of admin (if it is still "admin") and of the seed scripts' accounts (if it is still "testpass"), and logs a warning naming them. The seed scripts take SEED_PASSWORD from the environment or print a random one.
- Forge: a missing user_id gives the character to the caller; user_id 0 or an unknown id is 403. Stats and circle 1 are unchanged.
- create_campaign: the caller is the GM; an unknown user_id is 403, not a 500. The duplicate-code 500 remains. A code that reads as a number ("123", "-12", "1_000") is 422 "Campaign code must not be a number" (D13); codes like that already in the data still work, with their own channel key.
- join: still no status check, but only the character's owner can do it.
- rejoin: needs a rejoin invite or a dead character in that campaign (still no GM approval; the ink color quirk remains).
- circle-creation-state, roster and the notebook list: an unknown campaign is 404. Notebook writes with an unknown character or campaign are 404, not 500. role=GM and character_id in the notebook query are checked against the token.
- Behind Me can only target a character in the interceptor's campaign; an unknown target is 404 and costs nothing.
- Bug D2: gm_update_circle on circle 1 is 403 (circle 1 belongs to no campaign); SceneManager sends the campaign's circle id. The circle name is still not settable through it.
- GM powers come from the token, not payload.role, and GM circle messages only reach the GM's own campaign circle, so the resolve_circle fallback is no longer reachable that way.
- submit_assignment_report: only for the sender's own character (unknown ids are 404). There is still no reports_open check, and every player still receives every report. Fixed 2026-10-09 (playtest, reports-broadcast-all, report-forgets-sent): a report needs reports open, a second one needs replace (the form's Amend), and a report reaches only the Lightkeeper and its author. Tests: test_submit_assignment_report, test_reports_reach_only_the_lightkeeper_and_their_authors.
- update_circle is GM only, so the non-GM "may lower resources" branch and the string-resource crash from a player are gone. The milestone quirk remains.
- circle_relationship_respond on a GM socket is rejected (403) instead of ending the socket (bug D9).
- REST relationship propose now sets last_actor_id, and REST respond follows the WebSocket rule: only the party that did not act last may answer, and the answer records it as the last actor. Before, REST respond checked only the to-character's owner, so b could counter over the WebSocket and then accept its own counter over REST. The REST counter still keeps the original terms with status 'countered'.
- Chat: sender_name is set by the server; @Environment is GM only; a socket with no campaign cannot chat, so the cross-campaign whisper is gone. The ILIKE wildcard and the pending-sender echo quirks remain.
- WS add_notebook_entry only writes into the sender's own campaign; Lightkeeper entries are GM only.
- Notebook author fields: the server sets author_name (the character's name, or the GM's username, which is what the frontend sent), and on the WebSocket also pen_font, ink_color and character_id. A player must write as one of their characters in that campaign. Before, a member could sign an entry 'Lightkeeper' or with another player's name.
- All-digit campaign codes (D13): the character's owner gets the character channel with no campaign, the GM gets the campaign channel, and the connection manager keys them apart ("123" and "campaign:123"). With tokens a shared key was a real hole: either user could close the other's socket and receive its frames, including secret rolls and whispers. WS chat no longer looks up a campaign by the path segment either.
- apply_scar (D14): shift_down and shift_up must be two of the nine action ratings (engine.ALL_ACTIONS). Any other name is 403 and nothing is stored. With tokens the old behavior was a real hole: shifting campaign_id down, with scars_count as the other name, walked a player's own character into any lower-numbered campaign as an active member.
- A character_id of 0 or 1.5 is 404 (action_rejected). A bad character_id ('abc', object, list, true) still drops the frame.
- The 'gm' fallback channel no longer exists (closed with 4404), so its reset and end-assignment quirks are gone.
- The stale relationship-row quirk is still in the code, but whether the stale copy survives depends on when Python's garbage collector runs (the session's identity map holds weak references). The extra access-check queries changed that timing, so the test no longer pins it. ABILITY_MOD_DEFS is a local dict in the handler, and no current entry has both keys, so the order has no visible effect today. The real column types on the beta data copy were not checked either, because psql is not allowed here; the legacy-schema test pins what init_db produces instead.

## Fixed by the bug-fix stage (2026-10-04)

Each fix has its own commit, and its test was flipped or added in that commit.

- train_bonus and the other migrated column types: init_db's ALTERs now add the types the models declare (BOOLEAN DEFAULT FALSE for the flags, JSON for backstory_answers and ability_uses). On every start, convert_integer_flags turns any flag column that an older ALTER added as INTEGER into BOOLEAN (0 becomes false, anything else true) and leaves boolean columns alone. train_bonus had broken every forge and every train action on databases that got it through the old ALTER (live and beta were converted by hand on 2026-10-04). Existing TEXT copies of the JSON columns are not converted, because old rows may not hold valid JSON. Tests: test_init_db_converts_an_integer_train_bonus_to_boolean and test_model_column_types_match_the_database_after_init_db_on_a_legacy_schema.
- Endurance (bug D1): marks.py imports secrets, so take_mark's Endurance branch rolls one die per Nerve resistance pip left instead of ending the socket. Tests: test_endurance_six_keeps_the_character_standing and test_endurance_without_a_six_incapacitates.
- Assignment reports (the likely live bug): submit_assignment_report reads the circle row again under a row lock and writes a new dict, so a report is saved whatever backstory_answers already holds and reports from other sockets are kept. Each report is stored as {character_name, responses}, the shape of the broadcast, which the GM's report card reads after a reload. Reports saved before this fix are bare responses, so their card shows no answers. Tests: test_second_report_from_a_fresh_session_is_saved, test_reports_from_sockets_opened_before_any_report_are_all_kept, test_report_after_circle_answers_is_saved, and the stored shape in test_submit_assignment_report and test_report_onto_string_backstory_is_saved.
- GM notebook fetch: GET /api/notebook/{campaign_id}/entries treats an empty character_id (the frontend sends character_id= when it has no character) as absent instead of answering 422, which left the GM with an empty notebook. role=GM is still checked against the token, and a non-numeric value is still 422. Test: test_list_entries_with_an_empty_character_id.
- WebSocket frames that are valid JSON but not an object are ignored like invalid JSON instead of ending the socket. A null payload counts as an empty one, and a payload that is not an object gets action_rejected with status 422. Tests: test_non_object_frame_is_ignored, test_non_object_payload_is_rejected and test_null_payload_is_an_empty_one.
- update_gear with an item that is not text gets action_rejected 422 before anything is saved, instead of saving the gear and then ending the socket. Test: test_update_gear_non_string_item_is_rejected.
- circle_creation_vote and REST /circle/vote with an unknown vote_type are refused with 422 "Unknown vote type." before anything is stored, instead of committing the vote and then ending the socket or answering 500. Tests: test_circle_creation_vote_unknown_type_is_rejected and test_vote_unknown_type_is_422_and_not_stored.
- create_campaign with a code that is already in use is 409 "Campaign code is already in use" instead of a 500, including when another request takes the code between the check and the insert. Tests: test_create_campaign_duplicate_code_is_409 and test_create_campaign_when_another_request_took_the_code_first.
- Notebook calls with unknown ids: the login token stage had already made these 404 (see above), so no code changed here. A new test checks every notebook call (list, add, edit, delete, upload, with an unknown campaign, character or entry), including ids too large for an integer column: test_unknown_ids_are_404_on_every_notebook_call.
- GET /api/investigators/{id} for a character with no circle answers 200 with circle_id null instead of a 500. CharacterResponse.circle_id is optional now, so the OpenAPI snapshot changed for it. Test: test_get_investigator_with_null_circle.
- GET circle-creation-state for an unknown campaign: already 404 since the login token stage, with no code change here. The test now also checks that no circle is created, for an unknown campaign or for a refused caller (403), and covers an id too large for an integer column: test_circle_creation_state_unknown_campaign_is_404. For the GM and members the GET still creates the campaign's circle the first time.

The game rules were not changed. Places where the app's mechanics may differ from the rulebook (the zero-rating critical, Back Against the Wall, Premonitions and others) are listed in docs/refactor/RULES_CHECK.md for the game's owner to confirm.

## Fixed by the security review (2026-10-04)

A hand review of the sign-in and campaign access code (routers/auth.py, routers/campaigns.py, schemas.py). Each fix has its own commit and test.

- Rejoin after a death: the death path counted any dead character of the user tagged with the campaign. A player can kill their own pending character (four scars on its own socket), so anyone with the campaign code could join, die and rejoin with another character as an active member the GM never approved. Only an approved character that died and has not been replaced yet (status active) counts now, so one death opens the path once. Test: test_rejoin_after_a_death_needs_an_approved_character.
- Invite to rejoin: the username was matched ignoring case with .first() and no ORDER BY. Register compares usernames exactly, so "mira" and "Mira" can both exist, and the invite (which lets its holder rejoin without GM approval) could land on either one, whichever row PostgreSQL returned first. An exact match now wins; a name that matches only ignoring case must match one user, otherwise 409 "More than one player has that username. Please type it exactly, with the same capital letters." and nobody is invited. Test: test_invite_rejoin_case_variants.
- Look-alike usernames: register (and Sign in with Google's create) compared usernames exactly, so "Mira" could be registered next to "mira" and pass for that player wherever a name is typed or read. A new username must now differ from every existing one in more than case (400 "That identification is already claimed."), and the name Sign in with Google suggests follows the same rule. Login still compares the name exactly, and pairs that already exist are left alone. Tests: test_register_username_must_differ_in_more_than_case, test_create_with_a_username_taken_in_other_case and test_the_suggested_name_differs_from_taken_names_in_more_than_case.
- Register compared emails exactly. A case variant of someone's email ("ADA@example.test" next to "ada@example.test") made a second user with that email ignoring case, and Sign in with Google then linked neither of them by email, so the owner lost the one-step move to Google. Register now compares emails ignoring case (400 "That correspondence address is already registered."). Pairs that already exist are left alone. Test: test_register_email_must_differ_in_more_than_case.
- Login and the Google link took a password of any length, and passlib raises PasswordSizeError for more than 4096 characters, so such a request was a 500. Both now answer 422 for a password over 1024 characters (register allows 128). Tests: test_login_with_a_very_long_password_is_422 and test_link_with_a_very_long_password_is_422.
- A retired campaign still took joins (the character then waited as pending in a campaign nobody runs), rejoins (an invite sent before the retirement still made the character active in it) and new invites. All three are now 409 "This campaign has been retired.", after the caller's own access checks. Test: test_a_retired_campaign_takes_no_new_members.
- A login token stayed good for its 30 days whatever happened to the password, so replacing a password (retire_published_passwords, or a new hash set in the database) did not end the sessions of whoever knew the old one. Login tokens now carry a password stamp (`pwh`, a keyed hash of the password hash), and a token whose stamp no longer matches the user is refused like an invalid one. Tokens from before the stamp have none and are refused, so everyone logs in once more. Tests: test_a_new_password_ends_earlier_login_tokens and test_a_token_without_the_password_stamp_is_refused.
- Sign in with Google linked an account by email and left its password as it was. Register never checks that an email belongs to whoever registers it, so someone who registered another player's email first got that player linked into an account whose password (and login token) they had, and could log in beside them indefinitely. Linking by email now replaces the password with one nobody knows, which also ends every earlier login token (the password stamp), so the account belongs to the Google account alone from then on. Linking through /api/auth/google/link, which proves the password, keeps it. Tests: test_linking_by_email_shuts_out_whoever_registered_the_email, test_linking_with_the_password_keeps_the_password and test_a_matching_email_links_the_existing_user.
- Pending counted as membership. Anyone with a campaign code can join it, and the character waits as pending for the GM's approval, so a stranger with the code could read the roster, the notebook and the circle creation state, write notebook entries and uploads, vote and propose on the circle over REST, and chat or post rolls, marks and gear to the table, all before the GM said yes. The frontend never let a pending character onto the desk, and broadcast_campaign already left pending characters out. A member is now an active character only (`MEMBER_STATUSES`); the GM may still act on a pending one over the WebSocket (`ROSTER_STATUSES`), and approval makes it a member at once. Tests: test_a_pending_character_reaches_nothing_of_the_campaign, test_chat_from_a_pending_character_is_rejected, and the flipped pending cases in test_roster, test_circle_creation_state_for_gm_and_members_only and test_circle_creation_state_with_content.
- A character's socket sent the campaign's circle on connect whatever the character's status, so a pending character (anyone with the campaign code) or a retired one read the circle's name, scene, chapter house, backstory answers and assignment reports. The socket still opens with the campaign (an approval while connected makes it a member at once), but the circle_update on connect is the campaign's circle only for an active member; others get the shared circle 1. Test: test_a_non_member_does_not_get_the_campaign_circle_on_connect.
- Login and the Google link answered an unknown username at once but spent a bcrypt check on a known one, so the time taken told whether an account has that username (the link works with password login off, so it would still show there). Both now go through check_password, which lets passlib run its dummy check, as slow as a real one, when there is no user. Tests: test_login_checks_a_password_even_for_an_unknown_username and test_link_checks_a_password_even_for_an_unknown_username.
- The sign-in routes are async and ran bcrypt (about a quarter of a second per hash or check) on the event loop, so every login, register and Google link or create held up every game WebSocket of the single worker for that long. Every hash and check there now runs in a worker thread. Test: test_bcrypt_never_runs_on_the_event_loop.

## Fixed on 2026-10-06

- Negative drive spend (D15): a roll with a negative `drive_spent` raised the drive above its maximum (a player could refill their own drive at will), committed that, and then failed on the empty pool. `check_message` now refuses it with `action_rejected` 422 "Drive spent cannot be negative." before anything changes, on a player's roll and on the Lightkeeper's. A value that is not a number still answers `roll_error` as before, and spending more than the drive holds is still RULES_CHECK.md item 5, for the owner to decide. Tests: test_negative_drive_spent_is_rejected and test_negative_lightkeeper_roll_is_rejected; test_roll_bad_drive_spent_is_roll_error checks that `null`, text, `NaN` and JSON's `Infinity` still get `roll_error` with the socket open.
- Gilded choices (D8, rules batch 1): resolve_gilded took the kept value from the client, so any value could be claimed at any time and replayed, a non-numeric value ended the socket, and a secret roll's choice was logged to the whole table. The server now keeps the dice of the roll waiting for a choice and reads the kept die from them; a choice with nothing waiting is refused with `action_rejected` 409, and a secret roll's choice stays with the roller. A resistance reroll that waits for a choice no longer logs "? ." but a plain "burned resistance" line, and the kept die's line follows. Tests: test_resolve_gilded_reads_the_held_dice_and_cannot_be_replayed, test_resolve_gilded_ignores_a_value_that_is_not_a_number, test_a_secret_roll_shows_no_dice, test_burn_resistance_gilded_choice_logs_the_kept_die. The rules side is RULES_CHECK.md items 1 to 8.
- Marks and their offers (D5, D6 and rules batch 2): a declined soak or Death Defy lost the mark, Back Against the Wall blocked every Brain mark, Premonitions left the ally's mark, the Behind Me interceptor's soak offer had no options and never landed the mark, Adrenaline Rush could be claimed at will with no mark taken, an unknown mark_type was sent back as if it were a track (take_mark and intercept_mark now answer 422), and a JSON string in ability_uses ended the socket in take_mark and resolve_ability_mark (vtt/abilities.py reads the string's JSON). See RULES_CHECK.md items 9 to 12 and 21 to 24 for the rules side. Tests in test_ws_marks.py and test_json_strings.py, flipped in the same commit.
- Rolls (rules batch 3): any attribute name worked as a player's roll action (nerve_max fed the pool), a spend larger than the drive still added every die while the drive floored at 0, a mod listed twice was applied twice, Back Against the Wall's mark was capped at 3, and the roll's use counter never counted. A player's roll now names one of the nine actions (422 otherwise), an overspend is refused (422), each mod applies once, the mark goes through apply_mark, and the counter is gone. See RULES_CHECK.md items 5, 17, 21 and 25 to 29.
- Advancement (D12, rules batch 4): apply_advancement had no gate, so a player could advance any number of times, and an ability appended with "; " stopped exact-name ability checks from finding either ability. Picks now come from the Lightkeeper's circle advance (two per member, characters.advancement_picks) and are checked (RULES_CHECK.md item 14), and every ability check splits the field (vtt/abilities.py). On the desk, the advancement dialog's "Advancement Applied" slip now shows (FRONTEND.md quirk 3: clearing circleAdvancement hid it), and applyAdvancement no longer sends the never-set accessSession.characterId (quirk 4). Tests: test_apply_advancement_* in test_ws_character.py and test_an_advanced_ability_still_works.
- Circle resources (rules batch 5): a campaign circle's max_capacity and refill counted the members attached to the circle, and campaign members stay on circle 1, so it refilled each resource to 1. The members are now counted by campaign, and each resource refills to 1 plus them (RULES_CHECK.md item 16; on 2026-10-06 they were shared as one pool, corrected on 2026-10-07 from the rulebook's p. 62 example). The GM socket's refill, advance and end-of-assignment handlers read the circle row again before writing, because the socket's long-lived session could hold it as it was at connect: a refill after a rejoin used the old member count, and setting a value the stale copy already showed wrote nothing. Tests: test_refill_resources_counts_the_campaigns_members, test_advancing_the_circle_replenishes_its_resources, test_stamina_training_gilds_three_dice_an_assignment.
- Forge (rules batch 6): the client chose every stat with no bounds, so any request could make an investigator with ratings of 3, 9 in every drive, any gild, marks and scars, and a rating too large for the column reached the database and failed with 500.
